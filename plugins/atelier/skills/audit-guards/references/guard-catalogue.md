# Guard catalogue for LLM-driven software work (v3.3)

*Project-free reference. Every sentence is meant to be pasted, unchanged, into the kind named in "Lives in".*

## How this catalogue is used

1. This is an **audit checklist and a source of sentences**. It is never pasted whole into a prompt, and its own length is therefore not a defect -- no agent reads it whole.
2. Anthropic's own 2026 guidance: a bloated instruction file makes the real instructions be ignored; the target is **under 200 lines**, and longer files measurably reduce adherence.
3. Compliance drops past roughly **ten stacked constraints** (FollowBench / ComplexBench, RECAST 2026), and content in the middle of a long context loses up to 88 points of accuracy (positional-failure work, 2026).
4. Therefore: **per role, at most ~10-12 sentences are written locally in that role's definition.** Everything shared is the core block, included **by reference**, not copied.
5. Vendor consensus 2026: instruction text is **advisory**; hooks, sandboxes, permission rules and CI gates are **deterministic**.
6. So **every guard whose "Enforced by" ceiling is level 1 or 2 is built as a check, not written as prose** -- secrets, destructive commands, host mutation, file scope, test weakening, a red check, a dirty tree.
7. Prose is the residue: the guards whose ceiling is 3, 4 or 5 -- the ones no machine can decide -- are the ones that earn a line in a definition.
8. The audit procedure at the end is how the catalogue is actually applied to a project: one artefact at a time, one yes/no bit at a time.
9. `audit-guards` re-fetches every source in the Sources appendix at each run; a source whose page hash differs from the recorded one flags every guard citing it as **re-check**. That is a level-2 mechanical step -- it detects a changed page, it does not promise the evidence still holds. Eleven vendor pages carry a recorded hash since 2026-09-16 (sha256 of the raw HTML as fetched by `curl`; the re-check is the same command); the others still hold a placeholder.
10. A row whose Evidence cell reads **PROPOSED (H10 counter-check pending)** is a rule proposal, not a rule: it is audited as a follow-up at most, and it is pasted into no definition until the counter-check has passed and the mark is replaced by an evidence grade.

## Preface

1. A **guard** is a named failure class plus the one executable step that prevents it -- never a value, a virtue, or a piece of advice. So a guard names its failure class **generically** -- an auditor must be able to miss it in a web app, an API, a CLI, or a library -- and the concrete form appears inside the row as an example, never as the rule.
2. A guard is present only where an executor reads an **imperative sentence** AND something fails when the sentence was not followed. Prose describing the virtue is not the guard.
3. Six roles execute: **coder** (writes the change), **fixer** (repairs named findings), **reviewer** (judges a bounded diff), **tester** (drives the landed surface), **head** (cuts, briefs, decides the landing), **operator** (rules).
4. **Placement is KIND x READER, and nothing else.** Which file a kind is delivered in, and whether that file sits beside the project or beside the machine, is a delivery detail an installer or a hand copy settles -- never part of the rule. A file name is only the **platform's mailbox** for a kind. The one rule: **a rule lives where the one who executes it reads it.** For process rules a second question follows: **WHEN** the executor reads it -- at every moment (the always-loaded core) or at one step (a step-loaded skill). The reader table below settles who actually reads each mailbox on each platform, which is not always who the file name suggests.
5. **One core block.** The agent-behaviour rows shared by every executing role are delivered as ONE core block that each role definition **includes by reference**; only the role's own rows are written locally. Rows marked **CORE** below are that block. This is what makes a reworded row reach four definitions at once, and it makes H14's mailbox check a check on one file instead of N.
6. **One home per guard.** Where the head must act at dispatch for an agent's sentence to be executable, the row writes "head half: H1 pointer" rather than a second home. Where one failure class genuinely has two executors -- C12: the code classifies, the agent's own output must not leak; C24: the agent stops, the manifest change is gated -- the row names both halves and each half gets its own audit bit.
7. A kind with no executor (code rules, facts, enforcement configuration) never receives an output-contract or hard-limit sentence; the agent-facing half of such a guard is filed under agent behaviour instead.
8. **Product truth** -- requirements, decisions, ideas, work items -- lives with the product. An agent instruction that states what the *product* should do is misfiled product truth; a private note that carries a ruling is a ruling that exists for one session.
9. **Private notes** are what a head keeps for itself. Claude Code has memory; Cursor has memories; Codex and Copilot have no such place at all -- which is why no rule another agent or another machine must execute may live there. **Machine-local limits are not notes**: they are facts at machine scope, because a provider with no notes still has to honour them.
10. **Ruled sentences** = the written expectation the change must satisfy, on a ladder: a spec or acceptance criteria with IDs -> the item's done-when -> the brief's sentences. A project with none of the three yields the reviewer's first finding, "no ruled sentence to judge against", and the head writes the done-when **before** the review.
11. Severity vocabulary is fixed across every role: **blocking** (a defect this change introduces against a ruled sentence, a contract, or a repository rule -- always data safety, security, secrets, public contracts, failing checks) or **follow-up** (polish with no behavioural effect, pre-existing behaviour with unchanged evidence cited, or out of scope with its owning item named). `architectural` stops the lane and is never a follow-up.
12. A sentence the process contract already carries is not re-anchored here; it appears at the end under "Already in the contract -- verify wording". A row marked *extends* adds only its new clauses.
13. Every audit question is a **numbered list of bits**, each answerable yes or no on its own. A "no" on any bit is one finding and names that bit. A bit marked *(cross-artefact)* cannot be answered from the artefact under audit alone.
14. **The ladder exists because CI already holds the mechanical guards, and text is the weakest level there is.** Every row carries "Enforced by", strongest first: **1** CI gate, linter, coverage or traceability check (fails the pipeline); **2** hook or precondition (blocks before the action -- a pre-tool hook, a sandbox write-deny, the landing's dirty-tree precheck, a capped run wrapper); **3** output-contract field (the report must carry the field, so its absence is visible); **4** review question; **5** prose only. Each cell names the level a typical setup reaches **today** and the honest **ceiling** -- a rung that cannot be built is not written, because a ladder that names unbuildable rungs stops being a ladder.
15. **Evidence** on every row: **ESTABLISHED** (multiple independent 2026 sources, mostly vendor or peer-reviewed), **SUPPORTED** (a real documented trend, the specific mechanism extrapolated), **PLAUSIBLE** (consistent with the literature but overshooting or unmeasured), **HOUSE** (our own, from the failures of 2026-09-15/16 -- experience, not science), **CONTESTED** (the evidence points both ways), **PROPOSED (H10 counter-check pending)** (entered as a rule proposal with its source named; not yet a rule -- see "How this catalogue is used" 10; no row carries the mark in this version). Invented does not mean wrong; it means unbacked and therefore revisable.

### The seven kinds of rule, by their reader

| Kind | Who reads and executes it | What belongs in it | What must never be in it | Example |
|---|---|---|---|---|
| **Process** | The head, on every lane | How the head cuts, briefs, routes, reviews, lands; cadences; who decides what | A code-style rule; an agent's own output contract; a product decision | "One fix step repairs at most eight findings across at most six files." |
| **Agent behaviour** | One executing agent -- worker, fixer, reviewer, tester -- on every task | Its procedure, its output contract, its hard limits: what holds even when the brief forgot to say it | A fact about one project; a rule only the head can perform; what the product should do | "A step you did not run is written `not run: <reason>`." |
| **Code rules** | Anyone who writes or reviews code, a human included | Rules about the code itself: structure, error handling, naming, what the code must do at runtime | An output contract, a hard limit, a turn bound -- this kind has no agent executor | "A degraded or partial result is reported as degraded, never as success." |
| **Facts** | Any agent that has to operate this project or this machine | Commands, layout, what the gate runs, where identifiers are allocated, and **facts at machine scope**: the concurrency control's path, the local run caps, the worker cap | A second process order; a duplicated cadence; any rule that already lives in another kind | "The targeted check selection is `<command>`; the concurrency control is `<path>`; this machine runs at most four capped check runs." |
| **Enforcement configuration** | **The machine** | The checks that make a guard's level 1-3 real: CI config, pre-tool and pre-commit hooks, sandbox and permission deny rules, report parsers, coverage and traceability scripts | The rationale for the rule -- that stays with the rule; any sentence only a human executes | "A deny rule for a force-update of a published ref; a diff check failing an added skip marker." |
| **Product truth** | The head and the operator, when deciding what to build | Requirements, decisions, ideas, work items, ruled sentences with IDs, done-whens | Anything an agent must do on every task; anything that belongs to the code | "A guest checkout keeps its basket for 30 days." |
| **Private notes** | One head, for itself | Observations, operator calibration, candidate rules with an expiry, the pointer to where a rule now lives | Any imperative another agent or another machine would have to execute; any ruling; any product decision; **machine-local limits, which are facts** | "This operator wants disagreement said plainly; the rule itself lives in process." |

### Who actually reads each mailbox (per platform), and when

The file name says which kind a platform expects in it; it does not say who reads it. Settled by observation on 2026-09-16: a Claude subagent dispatched by the head had the user-level `CLAUDE.md` in its context -- so every worker on that platform carried the head's whole process contract. An audit that assumes "process file = head only" cannot see that, which is why this table exists.

| Mailbox (platform) | Who actually reads it | When it is loaded | Consequence for placement |
|---|---|---|---|
| User-level `CLAUDE.md` (Claude Code) | **The head AND every Claude subagent** it dispatches | Always, at every session and every subagent start | A head-only sentence here is read by every worker: word it so it is not a wrong instruction for a worker, or move it to a step skill. Its length counts against every worker's budget (H16). |
| Project `CLAUDE.md`, project rules files | Everyone working in that repository, any role, any provider that honours the file | Always | Facts, code-rule pointers, the project's own bounds. Never a role's procedure. |
| Agent definition (`agents/<role>.md`) | That one role, on every task it is dispatched for | At dispatch of that role | The role's own ~10-12 sentences plus the core block by reference. |
| Skill (`SKILL.md`) | Whoever loads it, at that step -- the head or a worker | At the step, by name | Step-bound process rules (dispatch, review cadence, landing, rule change). A rule needed before the step's own trigger is in the wrong skill. |
| `AGENTS.md` (Codex, Cursor, Copilot) | That provider's head and its workers alike | Always, hierarchically per directory | Same reader as the user-level `CLAUDE.md`: no head-only wording; a hard size cap on some platforms. |
| Memory / private notes | One head, on one machine | Always, for that head only | Never a rule another agent must execute (H11). |
| Hooks, permission rules, sandbox, CI | The machine | At every tool call / every push | Enforcement configuration only; the rationale stays with the rule. |

**The timing axis for process rules.** A process rule is either **always-loaded** (the head needs it at every moment: the loop, the roles, the limits, the checked receipt, the checked premise) or **step-loaded** (needed at one step: dispatch, fix batch, review verdict, landing, rule change, session start). Each process row's "Lives in" cell names which. Audit consequence: a step rule found only in the always-loaded file is a **misfiling** (`follow-up -- wrong mailbox`); a core rule found only in a step skill is a **gap** (`blocking -- missing`), because the head reaches the moment with the rule unloaded; and a step rule sitting in a skill whose trigger comes *after* the moment it governs (a plan-review-first rule inside a skill loaded on the review verdict) is the same gap.

## Using the catalogue as an audit

1. Take one artefact: an agent definition, a skill, a code-rules file, a policy file, a facts file, a CI or hook configuration.
2. Decide which kinds it is the mailbox for, and which role executes it -- **from the reader table, not from the file name**: a user-level `CLAUDE.md` is read by every Claude subagent, so it is audited as a worker's artefact too. **An artefact with no executor role -- code rules, facts, enforcement configuration -- is audited only against the guards whose "Lives in" names that kind.** A definition read by several roles is audited once per role.
2a. **For a process artefact, check the mailbox's timing.** For each process sentence name the moment the head needs it: every moment, or one step. A step rule found only in the always-loaded file is `follow-up -- wrong mailbox: <sentence> in <file> -> belongs in the <step> skill`. A core rule found only in a step skill, or a step rule in a skill whose trigger comes after the moment it governs, is `blocking -- missing` for the moment the head reaches with it unloaded.
3. **Walk the KIND, not the file.** Before marking a guard absent, open every artefact that delivers that kind -- the contract, the skills, the role definitions, the enforcement configuration. A cadence written verbatim in an audit's own definition is present, not missing.
4. Walk that kind's audit bits in order, one at a time, answering only yes or no. A "no" names the bit. A bit marked *(cross-artefact)* needs the other artefacts of the set open beside this one.
5. Answer yes only if an **imperative sentence** tells the executor what to do, and only if the step is **checkable** from the agent's output -- a named owner, a quoted command with its status, a per-finding status, a card field. Presence of prose is not presence of the guard: "look for reuse before writing" is not C1; "test thoroughly" is not C13 or T3.
6. Answer no when the sentence exists but lives in the wrong kind for this executor, or is unbounded (R3 without a cap, H2 without a count), or uses a vocabulary the rest of the system does not.
7. **Fire on surplus, not only on absence.** Walk the artefact's own sentences and file every one whose reader is not this kind's: a process sentence or an output contract inside a code-rules file, a product decision inside an agent definition, a cadence duplicated from the contract. The finding form is `follow-up -- misfiled: <the sentence> in <artefact> -> belongs in <kind>, whose reader is <role>`.
8. **"Does not apply here" is never an answer.** The row's concrete form is an example, not the rule: name the generic failure class, then look for the sentence in *this* project's own form -- an endpoint's status instead of an exit code, a schema instead of a state directory, a concurrency group instead of a file lock. Only after that may a guard be marked not applicable, with the reason written.
9. **Where a guard is present but incomplete, the finding names only the missing clause and the weaker sentence it replaces** -- never the whole paste, which would leave a duplicate next to the weaker line.
10. **Memory hygiene:** read the head's private notes as an artefact of their own. An imperative another agent or another machine would have to execute is misfiled; so is a ruling, a product decision, or a machine-local limit. File it against the kind that should hold it, and against the note that must shrink to a pointer.
11. **Then check the level, not only the presence.** A guard present but sitting at level 5 although its "Enforced by" cell names a higher level this project could build is a finding of its own: `follow-up -- weakly enforced: <guard #> in <artefact> at level 5 -> build level <n>: <the mechanism>`. A guard already at the honest ceiling its cell names is not a finding, however thin the prose beside it.
12. Output one finding per no, in exactly this form: `blocking|follow-up -- missing: <guard #> bit <n> in <artefact> -> consequence: <the failure class> -- add: <executable sentence> [replacing: <the weaker sentence>]`. Blocking is a guard whose absence lets a failure class through silently; follow-up is a guard present but misfiled, unbounded, or worded weakly.
13. Quote the executable sentence verbatim; do not paraphrase it into the artefact's own voice.
14. Where two artefacts would both carry the same sentence, file the finding against the kind the executor reads, and a second finding against the duplicate that must be removed. *(cross-artefact)*
15. A sentence from the "Already in the contract" list is never filed as missing; file a wording drift instead.
16. A row marked **PROPOSED** yields a follow-up at most, in the form `follow-up -- proposed guard absent: <guard #> -> pending H10 counter-check`; it is never a blocking finding and its sentence is never pasted until the mark is gone.
17. Return the findings as one list per artefact, blocking before follow-up.
