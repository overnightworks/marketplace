# Guard catalogue for LLM-driven software work (v2)

*Project-free reference. Every sentence is meant to be pasted, unchanged, into the file named in "Lives in".*

## Preface

1. A **guard** here is a named failure class plus the one executable step that prevents it -- never a value, a virtue, or a piece of advice.
2. A guard is only present where an executor reads an imperative sentence AND something fails when the sentence was not followed. Prose describing the virtue is not the guard.
3. Five roles execute: **coder** (writes the change), **fixer** (repairs named findings), **reviewer** (judges a bounded diff), **tester** (drives the landed surface plan-blind), **head** (cuts, briefs, decides the landing).
4. Seven places a rule can live: **process contract** (how the head works: roles, steps, cadence, landing), **agent definition** (worker, fixer, reviewer, tester: what an agent does on every task, its output contract, its caps), **coding and testing conventions** (rules about the code, not the process), **a plugin's own policy file** (the `AGENTS.md` of an agent plugin or library repository: code policy binding everyone who edits that repository, including a human), **project CLAUDE.md** (project facts only: commands, layout, checks), **plan / items** (product rulings, slices, cards), **memory** (observation only, plus machine-local limits and a pointer to the rule).
5. The one rule for choosing the place: **a rule lives where the one who executes it reads it.**
6. **One home per guard.** "Lives in" names exactly one layer. Where the head must do something at dispatch for a worker's sentence to be executable, the row writes "head half: H1 pointer" rather than a second home. A layer that carries no executor -- a conventions file, a plugin policy file -- never receives an output-contract or hard-limit sentence.
7. Consequence: a rule another agent or another machine must execute is misfiled in memory -- head half to the contract, agent half to the definition, code half to the conventions; memory keeps the pointer, the machine-local limit, and the evidence.
8. Consequence: the agent definition is the only layer that still holds when the head forgets the sentence in a brief; the contract is the only layer that holds when the head is a different provider's model.
9. A project CLAUDE.md never carries a second process order -- facts only; a duplicate process there is a defect, not redundancy.
10. Severity vocabulary is fixed across every role: **blocking** (a defect this change introduces against a ruled sentence, a contract, or a repository rule -- always data safety, security, secrets, public contracts, failing checks) or **follow-up** (polish with no behavioural effect, pre-existing behaviour with unchanged evidence cited, or out of scope with its owning item named). `architectural` stops the lane and is never a follow-up.
11. A sentence the process contract already carries is not re-anchored here. Those appear once, at the end of the catalogue, under "Already in the contract -- verify wording". A row marked *extends the contract's existing sentence* adds only its new clause.
12. The catalogue below is written so an audit can be run against any agent definition, skill, conventions file, policy file, or CLAUDE.md: walk the guards whose "Lives in" names that layer, and each "no" is one finding.

## Already in the contract -- verify wording, do not re-anchor

- **Blocking / follow-up vocabulary and the `architectural` stop** (v1 R2) -- verify the reviewer definition uses the contract's two values and no third word.

## What belongs where

**Sentences for a process contract (global CLAUDE.md / AGENTS.md).** How the head works; nothing about code style.
- Brief contents, in one sentence replacing the existing one -- H1 (carries C1, C5, C7, C11, C13, F5 into every dispatch).
- One cluster per fix step -- H2; slice size and the item at dispatch -- H3.
- Landing preconditions -- H4; freed items at every landing -- H5.
- Tester after a surface landing, with its routing row -- H7; audit anchors -- H8.
- The three questions a rule counter-check answers -- H10.
- Where a rule may live, and that memory is never a rule's home -- H11.

**Sentences for an agent definition (worker, fixer, reviewer, tester).** What the agent does on every task, whatever the brief says.
- Owner and family named before writing -- C1; cross-file leftovers, mirrors, IDs -- C5; identifiers -- F5.
- Lane isolation and own scratch, as Hard Limits -- C6; local runs and the shared lock -- C11; the self-stop -- C8.
- Self-drive fresh and repeated -- C7; criterion and its variants -- C13.
- Fix the cause in the owner -- F1; one status per finding -- F3; re-based tests -- F4; blocking-only scope -- F7.
- Ruled sentences plus `unproven:` -- R1; bounded decider count -- R3; never review your own work -- R5; confirmed findings versus questions -- R8.
- Plan-blind, real entry point, second run, error paths, card format -- T1 to T5.

**Sentences for coding and testing conventions, or for a plugin's own policy file.** Rules about the code, cited by writers and reviewers, and binding a human editor too.
- A mirror test module per source module -- C4.
- No silent success -- C9; delete the predecessor -- C10.
- Credential and secret egress -- C12; the surface's output contract -- C14.
- A plugin's `AGENTS.md` is this layer for its own repository: it carries C4, C9, C10, C12, C14 and never an Output Contract, a Hard Limit, or a cap.

**What a project CLAUDE.md may contain: facts only.**
- Commands: build, the targeted test selection, lint, typecheck, the capped wrapper, and the shared lock's path -- the concrete form of C7, C11, C13.
- Layout: package or module map, where mirror tests live, where specs live -- the concrete paths for C4, C5.
- Checks: what the gate runs and what it enforces.
- Identifier families and where they are allocated -- the concrete form of F5.
- A pointer to the conventions file and to the process contract. Never a second process order, never a duplicated review cadence, never a rule that already lives in the contract or the conventions.

## Using the catalogue as an audit

1. Take one artefact: an agent definition, a skill, a conventions file, a plugin policy file, or a CLAUDE.md.
2. Decide which layer it is, and which role executes it. **A conventions file or a plugin policy file has no executor role: walk only the concepts whose "Lives in" names that layer, and file every other concept against the layer that holds it, not against this artefact.** A definition read by several roles is audited once per role.
3. Walk that layer's audit questions in order, one at a time, answering only yes or no.
4. Answer yes only if an **imperative sentence** in the artefact tells the executor what to do -- not if the topic is merely discussed.
5. Answer yes only if the concept is **checkable**: a reader of the agent's output can tell whether the step happened (a named owner, a quoted command with its exit code, a per-finding status, a card field).
6. Answer no when the sentence exists but lives in the wrong layer for this executor. *This step needs the other artefacts of the layer set -- the process contract, the agent definitions, the conventions -- open beside the one under audit.*
7. Answer no when the sentence exists but is unbounded (R3 without a cap) or uses a vocabulary the rest of the system does not (a third severity word, T5).
8. **Where a concept is present but incomplete, the finding names only the missing clause and the weaker sentence it replaces** -- never the whole paste, which would leave a duplicate next to the weaker line.
9. Output one finding per no, in exactly this form: `blocking|follow-up -- missing: <concept #> in <file> -> consequence: <the failure class> -- add: <executable sentence> [replacing: <the weaker sentence>]`. Blocking is a concept whose absence lets a failure class through silently; follow-up is a concept present but misfiled, unbounded, or worded weakly.
10. Quote the executable sentence from the catalogue verbatim; do not paraphrase it into the artefact's own voice.
11. Where two artefacts would both carry the same sentence, file the finding against the layer the executor reads, and a second finding against the duplicate that must be removed. *This step needs both artefacts.*
12. A sentence from the "Already in the contract" list is never filed as missing; file a wording drift instead.
13. Presence of prose is not presence of the concept. "Look for reuse before writing" is not C1; "test thoroughly" is not C13 or T3. The executable form plus a check that fails when it is absent are what count.
14. Return the findings as one list per artefact, blocking before follow-up.
